รันรอบติดตามสำหรับ: $ARGUMENTS

คุณคือ orchestrator ของรอบทบทวน ต่างจาก `/research-stock` ตรงที่รอบนี้ **ไม่ได้ research ใหม่ทั้งหมด** แต่เอาสิ่งที่รอบก่อนคิดไว้มาตัดสินด้วยหลักฐานใหม่ของสัปดาห์นี้

**หลักการที่ห้ามพัง:** reviewer เป็นผู้ตัดสิน ไม่ใช่ผู้ตั้งใหม่ — มันแก้ทฤษฎี/verdict/entry_plan เองไม่ได้ ทำได้แค่ยกธงให้ทีม analyst/theorist ทำรอบใหม่ ถ้าปล่อยให้ผู้ตัดสินขยับคำทำนายเองทุกสัปดาห์ ทฤษฎีจะไหลตามราคาจนไม่มีอะไรผิดได้เลย และการติดตามทั้งระบบจะไร้ความหมาย

**กติกาประหยัด token:** researcher = sonnet, reviewer = opus (กำหนดในไฟล์ spec แล้ว ห้าม override) — รอบติดตามส่วนใหญ่จบที่ 2 agent นี้ ไม่ต้องเรียก analyst/theorist; ระหว่างรอ agent อย่าโพสต์สถานะยาว

1. **เตรียม workspace**: `DIR = pipeline/output/<TICKER>-review-<YYYY-MM-DD>` สร้าง directory ถ้ายังไม่มี

2. **ดึงความจำของรอบก่อน**:
   ```
   node scripts/prev-context.mjs <TICKER> > <DIR>/prev-context.json
   ```
   ถ้าสคริปต์บอกว่าไม่พบ ticker ใน DB แปลว่ายังไม่เคย research — หยุดแล้วบอก user ให้รัน `/research-stock <TICKER>` ก่อน

3. **เช็คราคาและเกณฑ์แข็ง** (ไม่ใช้ agent):
   ```
   node scripts/price-delta.mjs <TICKER> --json > <DIR>/price-delta.json
   ```
   อ่านผล ดู `escalate_reasons` และ `price_suspicious` — ถ้า `price_suspicious` เป็น true อย่าเชื่อราคานั้น ให้บอก user ว่าดึงราคาผิดตัวและข้ามการใช้ราคาในรอบนี้

4. **Research team (โหมดติดตาม)**: spawn `stock-researcher` โดยบอกใน prompt ว่า:
   - นี่คือ **รอบติดตาม** ให้ค้นเฉพาะของใหม่ตั้งแต่ `last_activity_on` ใน prev-context.json ถึงวันนี้
   - ให้ agent `Read` ไฟล์ `<DIR>/prev-context.json` เอง แล้วเล็งค้นไปที่ `theories[].assumptions/catalysts/risks` (ข้อความที่ต้องตัดสิน) และเลี่ยงของที่มีใน `known_items` แล้ว
   - เขียนผลลง `<DIR>/research.json`
   - ย้ำว่าถ้าสัปดาห์นี้ไม่มีของใหม่จริงๆ ให้ส่ง `research_items: []` ได้เลย ไม่ต้องขุดของเก่ามาใส่

4.5. **เช็ค hint** (ประเด็นที่กระทบกว้างกว่าหุ้นตัวนี้): ถ้า `research.json` มี `hints` ไม่ว่างเปล่า ให้ทำต่อไปนี้ต่อ hint แต่ละอัน **ก่อน** ไปขั้น 5 — เกณฑ์และวิธีเหมือน `/research-stock` ขั้น 2.5 ทุกอย่าง:
   - รัน `node scripts/list-hints.mjs` เช็คว่ามีรายงานเรื่องเดียวกัน/คล้ายกันใน 30 วันที่ผ่านมาหรือไม่ (เทียบหัวข้อ/`dek` ด้วยวิจารณญาณ ไม่ต้องตรงคำเป๊ะ) — ซ้ำ = ข้าม
   - ถ้าไม่ซ้ำและยังมั่นใจว่าผ่านเกณฑ์จริง: spawn `hint-analyst` (model fable — แพง ใช้เฉพาะที่ผ่านเกณฑ์จริง) ส่ง title, why_it_matters, evidence, `discovered_from` = ticker นี้, `run_date` = วันที่รอบนี้ สั่งเขียนลง `<DIR>/hints/<slug>.json`
   - ตรวจไฟล์ว่ามี `slug`, `title`, `content_md` แล้วรัน `node scripts/ingest-hint.mjs <DIR>/hints/<slug>.json`
   - **ถ้า hint ใหม่นั้นเกี่ยวข้องกับหุ้นตัวนี้จริง** ให้แนบสรุปสั้นๆ + `slug` + `direction`/`magnitude` ไปใน prompt ของ reviewer ในขั้น 5 ด้วย ใช้เป็นหลักฐานประกอบการตัดสิน claim ได้ และถ้ามันหนักพอก็เป็นเหตุผลของการยกธง `escalate` ได้ — แต่ reviewer ยังแก้ทฤษฎี/verdict เองไม่ได้ตามเดิม
   - ปกติจะไม่มี hint เลย ซึ่งเป็นเรื่องที่ควรเป็น — อย่าลดเกณฑ์ลงเพราะเป็นรอบติดตามที่ไม่ค่อยมีอะไร

5. **Review team**: spawn `stock-reviewer` โดยส่ง path ทั้ง 3 ไฟล์ (`prev-context.json`, `price-delta.json`, `research.json`) + วันที่ของรอบนี้ สั่งเขียนผลลง `<DIR>/review.json`
   - ถ้าขั้น 3 มีเกณฑ์แข็งยกธงไว้ ให้บอก reviewer ว่าต้องอธิบายในสรุปว่าเรื่องนั้นกระทบทฤษฎีหรือไม่อย่างไร (ห้ามเงียบ) และใส่ `"rule"` ไว้ใน `escalated_by`
   - **ห้ามส่ง research ทั้งก้อนเก่าให้ reviewer** — มันต้องตัดสินจากทฤษฎีเดิม + ของใหม่เท่านั้น
   - ย้ำให้ reviewer ตอบ `plan_status` + `action_md` โดยเทียบราคาปัจจุบันกับ `entry_plan.tranches` ใน prev-context จริงๆ (ingest จะปฏิเสธไฟล์ที่ไม่มี 2 ฟิลด์นี้)
   - ทุก check ต้องมีคำอธิบาย 4 ช่อง `if_md` / `then_md` / `because_md` / `so_md` (so_md เว้นได้เฉพาะ too-early) สำหรับหน้า `/track-record` — `then_md` ต้องมาจากทฤษฎีเดิมเท่านั้น (ingest ปฏิเสธไฟล์ที่ขาด)

6. **บันทึกลง DB**:
   ```
   node scripts/ingest-review.mjs <DIR>/review.json <DIR>/research.json
   ```
   สคริปต์จะปฏิเสธไฟล์ที่ `claim` ไม่ตรงกับข้อความเดิมเป๊ะ หรือเปลี่ยน status โดยไม่มีลิงก์หลักฐาน — **ถ้าโดนปฏิเสธ ห้ามใส่ `--force` เพื่อให้ผ่าน** ให้ส่งกลับไปแก้ที่ reviewer (ปกติคือมันเรียบเรียงข้อความใหม่แทนที่จะคัดลอกมา)
   Turso เขียนตรงขึ้น production อยู่แล้ว ไม่ต้อง deploy

7. **ตัดสินว่าต้องทบทวนใหญ่ต่อไหม** — รัน `/research-stock <TICKER>` เต็มรูปแบบต่อ **เฉพาะเมื่อ**:
   - `stance` = `escalate` (reviewer ยกธงเอง) **หรือ**
   - มี check ไหน status = `broken` **หรือ**
   - เกณฑ์แข็งเชิงโครงสร้างจากขั้น 3: ครบ 8 สัปดาห์ตั้งแต่ full run ล่าสุด / มีงบใหม่ออกในสัปดาห์นั้น

   **ราคาขยับ ≥7% หรือเข้าโซนไม้ลึกเพียงอย่างเดียว ไม่ใช่เหตุให้รันใหม่** — มันเป็นเหตุให้ reviewer ต้องตรวจให้ละเอียดขึ้นและอธิบายให้ได้ว่าทำไมราคาขยับโดยทฤษฎีไม่เปลี่ยน (ถ้าทฤษฎีเปลี่ยนจริง reviewer จะยกธงเอง) — ราคาไม่ใช่หลักฐาน มันคือสิ่งที่ทฤษฎีพยายามอธิบาย
   เวลารัน `/research-stock` ต่อ ให้ใส่ `"review_id": <id จากขั้น 6>` และ `"run_type": "update"` ลงใน `run` ของ bundle.json ก่อน ingest เพื่อผูก timeline ว่ารอบใหม่นี้เกิดจากการทบทวนครั้งไหน

8. **สรุปให้ user** สั้นๆ โดย**ขึ้นต้นด้วย `action_md` เสมอ** (คนอ่านถามก่อนว่าต้องทำอะไรไหม) ตามด้วยจุดยืน (ยืนยันเดิม / น้ำหนักเปลี่ยน / ทบทวนใหญ่), ข้อความที่เปลี่ยนสถานะพร้อมเหตุผลหนึ่งบรรทัด, ราคาเทียบรอบก่อน, ข่าวใหม่กี่ชิ้น — ถ้าขั้น 4.5 ทำ hint สำเร็จ ให้บอกแยกต่างหากชัดเจนว่าเจอ hint อะไรและดูได้ที่ `/insights/<slug>`
   - **สัปดาห์ที่ตอบว่า "ไม่มีอะไรเปลี่ยน" คือผลลัพธ์ปกติและถูกต้อง** รายงานตรงๆ ไม่ต้องขยายความให้ดูเหมือนมีงานเยอะ
   - ปิดท้ายเตือนว่าเป็นการศึกษา ไม่ใช่คำแนะนำการลงทุน
